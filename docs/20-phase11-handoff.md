# تحویل فاز ۱۱ — اسپلش لوگو، ضد دوبار‌کلیک و اسکلت لودینگ

## خلاصه
۱. **اسپلش لوگو** هنگام باز شدن وب‌اپ (یک بار در هر نشست).
۲. **اسپینر + قفل دوبار‌کلیک** روی همهٔ دکمه‌های ارسال فرم؛ و **ایمنی سمت سرور** تا حتی اگر درخواست تکراری برسد، خطای «این سانس دیگر در دسترس نیست» نیاید.
۳. **گام ۱ بهینه‌سازی: اسکلت لودینگ** + اندازه‌گیری پایهٔ سرعت. (طبق دستور: تبدیل تصاویر به WebP/AVIF هنوز **انجام نشده** و منتظر تأیید شماست.)

بدون متغیر محیطی جدید و بدون migration. مثل قبل: `npm ci` ← `npm run db:migrate` ← `npm run db:seed` ← `npm run build && npm start`.

## رفتار اسپلش
- فقط وقتی کوکی نشستی `hb_splash` نباشد نمایش داده می‌شود (هر بار بستن کامل مرورگر/اپ نصب‌شده = نشست تازه).
- اگر کوکی‌ها مسدود باشند، در هر بارگذاری کامل نمایش داده می‌شود (بی‌خطر).
- اگر JS اجرا نشود، انیمیشن CSS بعد از ~۳٫۶ ثانیه آن را پنهان می‌کند؛ هرگز گیر نمی‌کند.

## اسکلت لودینگ و کد وضعیت HTTP (نکتهٔ مهم)
`loading.tsx` باعث می‌شود پاسخ استریم شود و `notFound()` یا `redirect()` دیگر نتوانند کد وضعیت را عوض کنند (۲۰۰ می‌ماند). بنابراین:
- **لیست‌های عمومی** (سالن‌ها، سانس‌های باز، تیم‌ها): اسکلت با `Suspense` داخل صفحه؛ تیتر و فیلتر فوری می‌آیند، فقط نتایج اسکلتی‌اند. این صفحات هیچ‌وقت ۴۰۴/ریدایرکت ندارند.
- **صفحات جزئیات عمومی** (سالن، سانس، تیم، بازیکن) و بخش‌های مالک/ادمین/چت/رزرو/پرداخت: عمداً بدون `loading.tsx`؛ ۴۰۴ واقعی حفظ شد (E2E فازهای ۲ و ۳ و ۶ و ۹ این را بررسی می‌کنند).
- **صفحات خصوصی ساده** (پروفایل، علاقه‌مندی‌ها، اعلان‌ها، داشبورد): `loading.tsx`؛ مهمان‌ها را `src/proxy.ts` قبل از رندر با ۳۰۷ واقعی به `/login?next=…` می‌فرستد. proxy فقط وجود کوکی `hb_session` را می‌سنجد؛ احراز هویت واقعی همچنان در صفحه/اکشن است.
- ⚠️ هرگز `src/app/loading.tsx` (ریشه) نگذارید.
- ⚠️ گروه مسیر `(list)` برای محدود کردن `loading.tsx` امتحان شد ولی Next/Turbopack خطای «client reference manifest» داد؛ از آن استفاده نشد.

E2E فاز ۱۱: اسپلش (نمایش، محو شدن، کوکی نشستی، عدم نمایش مجدد، نشست جدید، بدون JS، reduced-motion)؛ دکمه‌ها (غیرفعال، `aria-busy`، اسپینر چرخان، کلیک/Enter مکرر ← فقط یک رزرو و یک پرداخت، آزاد شدن قفل بعد از خطا)؛ اسکلت (با قفل واقعی جدول دیتابیس، داده کند می‌شود و اسکلت دیده می‌شود)؛ کدهای HTTP (۴۰۴ برای ناموجود، ۳۰۷ برای مهمان، ۲۰۰ برای عمومی‌ها).

### چطور خودتان سایت روی Vercel را تست کنید
1. **PageSpeed Insights**: <https://pagespeed.web.dev> ← آدرس سایت ← «Analyze» (موبایل و دسکتاپ؛ داده از سرورهای گوگل، نزدیک‌تر به واقعیت).
2. **Chrome DevTools**: پنجرهٔ Incognito ← F12 ← تب Lighthouse ← Mode: Navigation، Device: Mobile ← Analyze. (افزونه‌ها را خاموش کنید.)
3. **WebPageTest**: <https://www.webpagetest.org> ← یک مکان نزدیک (مثلاً اروپا) و Moto G / 4G.
هر آزمون را ۲–۳ بار اجرا و میانگین بگیرید. اولین بازدید بعد از deploy ممکن است کندتر باشد (cold start).

## محدودیت‌های شناخته‌شده
- `loading.tsx` برای جزئیات عمومی و بخش‌های مالک/ادمین عمداً نیست (کد وضعیت)؛ ناوبری به آن‌ها اسکلت ندارد و صفحهٔ قبلی تا آماده شدن می‌ماند.
- اسپلش با مرورگری که کوکی را مسدود کند هر بار نمایش داده می‌شود.
- قفل فرم بعد از بازگشت از bfcache آزاد می‌شود (`pageshow`)؛ در مرورگرهای خیلی قدیمی بدون `WeakSet`/`pageshow` بررسی نشده.
- اسکریپت `npm run db:reset` در package.json به فایل `src/db/reset.ts` اشاره می‌کند که در zip دریافتی **وجود ندارد** (از قبل). برای ریست از `dropdb/createdb` + `db:migrate` + `db:seed` استفاده کنید.
- پرداخت همچنان **شبیه‌سازی‌شده** است.

## مراحل استقرار (Vercel)
1. فایل‌های فاز ۱۱ را روی GitHub push کنید (`git add -A && git commit -m "Phase 11" && git push`).
2. Vercel خودکار build می‌گیرد (`vercel-build` ← migrate ← next build). متغیر یا migration جدیدی لازم نیست.
3. بعد از deploy: سایت را در پنجرهٔ ناشناس باز کنید ← اسپلش را ببینید ← یک رزرو با دوبار‌کلیک سریع بزنید ← فقط یک رزرو ساخته شود.
4. (یادآوری) رمز دیتابیس Neon را که در لاگ پیست شده بود **عوض کنید**.
